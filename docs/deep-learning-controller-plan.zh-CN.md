深度学习复用现有 Controller 底层的调整方案

日期：2026-10-28。代码基线：v0.9.6，提交 23ce0dd。状态：已按本方案调整代码，纳入 v0.9.7；按用户要求未运行本地测试或桌面实测。

目标是让深度学习通过现有 easy_uiauto 底层执行交互，并显示操作方框。底层缺少的方法补进 Controller 和现有绘框组件，由学习调用。人工录制继续独立工作，不关联知识库，不改变录制文件格式和用户已实测通过的监听、高亮跟踪行为。

根据用户最新指定，基础操作统一使用当前环境的 uiautomation 库。已读取并核对 J:/github/easyautomation/.venv/Lib/site-packages/uiautomation/uiautomation.py。项目通过正常包导入调用其接口，不复制该文件，也不直接修改虚拟环境中的第三方源码。Controller 作为项目统一入口，封装该库已有能力；缺少的组合操作在 Controller 内补齐。

这里区分人工录制与录制回放：人工录制监听真实操作；回放通过 ctrl.run_action 和 Controller 自动操作。需要统一的是深度学习与回放的动作执行，以及它们使用的绘框基础能力。

当前代码的调用关系和问题如下。

| 位置 | 当前行为 | 本次需要调整的内容 |
| --- | --- | --- |
| interaction_learning.learn_command_effect | 调用 ui_cli.execute，未开启 highlight | 深度交互默认开启操作预览，并统一管理绘框与截图顺序 |
| ui_cli._perform_action | 自行调用 UIA Click、PyAutoGUI 单击、双击、右击和移动 | 改为调用 Controller 共用执行入口 |
| ui_cli._paste_text_with_clipboard | 自行点击、全选、粘贴和复制读回 | 实际输入动作使用底层方法，学习层保留结果判定 |
| interaction_learning._attempt_recovery | 直接发送 ESC 或移动鼠标 | 恢复动作同样通过 Controller |
| scanner._activate_window | 自行恢复最小化、激活窗口和检查前台 | 将已有按句柄激活能力归入底层，扫描和学习调用它 |
| ctrl.Controller | 现有接口主要接收 LOCATION，内部再次查找控件，返回消息字符串 | 补充已定位目标入口和明确的执行结果，保留现有兼容接口 |
| ctrl.show_ctrl_area、draw.ScreenLineBox | 已有同进程 Tk 绘框能力，缺少完整的调用方生命周期控制 | 补充显示就绪、暂隐、关闭和退出通知，供学习流程使用 |

推荐的职责划分是：学习层负责选目标、校验知识、判断效果和保存记录；Controller 负责实际输入、窗口激活和调用绘框；ScreenLineBox 负责绘制。两种自动执行入口都到达同一个 Controller 动作实现。

录制回放 → 原有定位入口 → Controller 共用执行方法 → uiautomation。

深度学习 → 知识定位与校验 → Controller 共用执行方法 → uiautomation。

以下基础能力已从用户指定的本地源码确认，实施时直接复用。

| 基础操作 | uiautomation 已有接口 | 封装要求 |
| --- | --- | --- |
| 控件单击、双击、右击、中击 | Control.Click / DoubleClick / RightClick / MiddleClick | 使用本次已定位控件，避免再次查找 |
| 屏幕坐标点击 | Click / RightClick / MiddleClick | 供图像定位目标使用，与控件内偏移明确区分 |
| 悬停和移动 | Control.MoveCursorToInnerPos、MoveTo | 不附带点击 |
| 拖拽和鼠标按下/释放 | DragDrop、PressMouse / ReleaseMouse 及右键、中键对应方法 | 复用基础能力，本次不扩大自主探索的动作范围 |
| 滚轮 | WheelUp / WheelDown | 保留方向和次数参数 |
| 按键和组合键 | SendKeys、PressKey / ReleaseKey | 将旧接口的键名映射到该库约定；异常时释放已按下的修饰键 |
| 写入控件文本 | GetValuePattern().SetValue | 检查布尔返回值，保留写后读回验证 |
| 文本剪贴板 | GetClipboardText / SetClipboardText | 配合 SendKeys 完成粘贴、复制；检查写入结果并恢复已备份的文本 |
| 窗口激活 | 顶层控件 SetActive、SetForegroundWindow、GetForegroundWindow、IsIconic、ShowWindow | 保留当前句柄身份，并检查真正获得前台；仅按需恢复最小化 |
| 工作线程初始化 | UIAutomationInitializerInThread | 在使用 UIA 的线程中初始化，控件和 Pattern 在同一线程创建、读取和释放 |

该版本没有模块级 DoubleClick(x, y)。纯坐标双击由 Controller 按现有 Control.DoubleClick 的方式组合 Click 与 GetDoubleClickTime，无需另引入 PyAutoGUI。控件版 DoubleClick 直接使用现有方法。

需要特别遵守两个已确认的接口约定：Control.Click(x, y) 的 x、y 是控件内偏移，模块级 Click(x, y) 接收屏幕坐标；SendKeys 会解析花括号和修饰键语法，普通文本优先用 ValuePattern 或文本剪贴板输入，不能将用户文本直接当作快捷键表达式。

该库部分动作没有成功返回值，部分返回布尔值。封装应分别检查前置条件、异常和布尔失败；无异常不能替代学习层的效果验证。原接口参数含义保持兼容，不因更换基础调用而把文本输入变成命令输入或把控件偏移当成绝对位置。

1. 在原 Controller 内抽取共用执行方法，保留现有调用方式。

   从现有 left_click、right_click、double_click、mouse_move_control 等方法中抽取实际执行部分。原方法继续接收现有参数、执行定位，再调用共用方法；深度学习使用已验证目标直接进入同一个共用方法。每类动作只保留一个实际执行实现。

   原顶层函数、ctrl.run_action、ACTION / LOCATION 格式和现有消息返回保持兼容。新增的已定位入口直接返回明确的执行结果或抛出异常，学习层不再通过中文成功字符串或全局消息级别判断成败。

   原因：直接调用旧接口会再次定位，可能出现学习校验的是一个控件、实际执行重新找到了另一个控件。抽取共用执行部分，才能同时满足复用用户底层和避免重复定位。

2. 补充“已定位目标”的底层调用能力。

   学习层将本次校验获得的控件对象、所属窗口句柄、当前矩形及必要的动作参数交给 Controller。图像/OCR 定位没有 UIA 控件时，交给底层的是本次校验所得的矩形、窗口归属和定位来源。

   - UIA 目标沿用现有控件点击、双击、右击等执行方式，不重新解析 XPath。
   - 纯图像目标由底层提供坐标执行能力；坐标来自本次定位结果，不能使用历史截图位置直接执行。
   - 底层统一处理控件内偏移、屏幕坐标和多显示器坐标，保留原接口的坐标约定。
   - 窗口失效、控件不可操作或动作失败时，返回明确错误；不隐式跳转到其他目标。
   - 控件在当前执行线程内使用，不通过绘框队列把 UIA 对象再交给新的工作线程。

   原因：复用底层不应丢掉学习已经完成的目标验证，也不能为了调用一个旧接口而制造第二次查找。

3. 按实际缺口补充底层方法。

| 能力 | 实施方式 | 保留的语义 |
| --- | --- | --- |
| 单击、双击、右击 | 从已有 Controller 方法抽取共用执行部分，使用 uiautomation 的控件或坐标方法 | UIA 控件沿用已有操作方式；图像目标使用底层坐标分支 |
| 悬停 | 复用 mouse_move_control / mouse_move_pos，使用 MoveCursorToInnerPos / MoveTo，补已定位入口 | 悬停只移动鼠标，不附带点击 |
| 普通按键、组合键 | 保留原键名兼容层，统一调用 SendKeys 或 PressKey / ReleaseKey，补“当前已确认窗口内发送”的入口 | ESC 恢复不为了发送按键再次点击菜单项 |
| 文本输入 | 保留输入语义，使用 ValuePattern.SetValue 或 GetClipboardText / SetClipboardText 配合 SendKeys | 原“输入文本”行为保留；全选替换是单独明确的操作 |
| 按句柄激活窗口 | 将 scanner 的激活策略归入底层，使用 uiautomation 提供的窗口方法与前台读回 | 保留已验证窗口身份和最大化状态，必要时仅恢复最小化 |
| 实时方框 | 扩展现有 show_ctrl_area / ScreenLineBox 的控制能力 | 使用同进程绘制，穿透点击且不抢焦点 |

   文本读回中用于验证的全选、复制、End 等输入动作也必须由底层发出；读取文本和比较预期值仍可由学习层负责。底层调用完成与业务结果验证成功分别报告，不能把“按键已发出”直接记作“文本正确”。

   文本剪贴板操作在底层集中管理，使用 uiautomation 的读写接口保存和恢复文本，不宣称保存了所有剪贴板格式。补充文本能力不会自动扩大 explore_application 的候选动作范围。

4. 深度学习默认显示操作方框，绘框沿用现有组件。

   为深度学习增加可配置的 highlight，默认开启。方框显示的是本次已经定位和校验的目标。使用已有 ScreenLineBox 的视觉样式、点击穿透和不抢焦点行为；人工录制现有的持续跟踪保持独立。

   绘框接口补充显示就绪、暂隐/恢复、关闭、关闭完成等状态。调用方获得可控制的预览对象，Tk 窗口及回调始终由创建它们的线程管理。目标矩形在操作线程中获取，绘图线程只接收坐标等普通数据。

   建议每步按以下顺序执行：

   取得干净的操作前截图 → 定位并校验目标 → 显示方框并确认显示就绪 → Controller 执行动作 → 关闭方框并确认已消失 → 等待界面稳定 → 保存操作后截图与效果。

   对文本写入过程中的局部截图，以及稳定性检测使用的截图，同样通过暂隐/关闭机制排除本次绘框。不能只依靠固定等待 900 ms 猜测方框已经消失。

   若绘框初始化失败，在动作尚未执行时明确报告并停止本次交互；若动作已经执行后绘框清理失败，必须保留“动作已执行”的事实，效果记录标为未确认，不自动重做动作。关闭请求应在 finally 中处理，避免失败后遗留方框。

   原因：用户需要看见当前操作目标，学习需要干净的前后证据。绘框生命周期必须显式管理，防止方框颜色和位置变化被误判为软件功能效果。

5. 完整收拢学习流程中的输入动作。

   ui_cli._perform_action 改为动作适配入口，负责参数映射和读取底层结果。ui_cli 的剪贴板输入、interaction_learning 的 ESC 恢复与鼠标移出、scanner 的窗口激活都调用 Controller。

   批量语义命令也复用这一路径，因为 execute_batch 同样调用 _perform_action。正常流程和 fast 路径都要覆盖，避免只改逐条命令、遗漏批量执行。

   学习模块可以继续直接读取 UIA 属性、截图、识别图像、计算变化和写入知识库；实际改变界面的鼠标、键盘、文本写入和窗口激活动作统一由 Controller 调用 uiautomation。原 Controller 中相关的 PyAutoGUI 和 pyperclip 动作也归入这次替换范围，保证回放与学习最终调用相同基础能力。截图等只读功能可保留现有实现，静态检查按实际调用用途判断。

6. 保留学习特有的校验与效果记录。

   知识状态、语义一致性、参考图片、定位降级、操作后稳定性、前台干扰识别、前后截图和效果说明继续由学习层负责。动作执行结果与业务效果分开保存。

   共用底层结果至少能说明动作是否发出、使用的方法、目标类型和失败原因。发生异常时区分未执行、已执行但效果未确认、已验证成功，避免重复点击或重复写入。原有回放接口可将结果转换为现有消息，学习接口直接消费结果。

   本次不会增加人工录制与知识库的关联、自动将人工动作标为验证通过，也不引入人工录制与自主探索并行运行。两者并行涉及 ESC 来源等问题，属于独立需求。
